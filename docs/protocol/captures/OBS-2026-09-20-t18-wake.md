# OBS-2026-09-20-t18-wake

Task T18, on the ONE V5 with the PWR UPS. **The UPS powers the machine on at the scheduled
time, and clears the schedule once it has fired.**

Full output: [`t18-2026-09-20-wake.log`](t18-2026-09-20-wake.log) (identifiers redacted).

## Method

`sudo argonctl poweroff --wake-at "now + 20 minutes"`, run by the operator on mains with
argon-utils 0.1.24 in mode `full`. argond set the wake, read it back from the UPS, and scheduled
the poweroff a minute later. The machine powered off; nothing else touched it.

## Result

| | |
|---|---|
| Wake asked for | 2026-09-20 19:14 local (17:14 UTC, as the UPS holds it) |
| Poweroff | 18:55 local, a minute after the request |
| Machine back up | **19:14:22** (`uptime -s`), about 19 minutes off |
| argond's first wake check, 19:14:27 | **"no wake schedule set"** |

- **`ARGON-UPS-WAKE-MECHANISM`: the wake works.** The UPS powered the Pi on within half a minute
  of the minute it was given -- the schedule has minute resolution, so that is on time. The Pi's
  own firmware plays no part: `WAKE_ON_GPIO=0`, and the machine was in `POWER_OFF_ON_HALT` state.
- **`ARGON-UPS-WAKE-CLEAR`: a fired schedule clears itself.** argond found no schedule five
  seconds after boot, so the safety net had nothing to park. A wake therefore does not repeat
  daily or come due again on the running machine.

## Also seen

argond's first clock check ran one second into the boot, before the system clock was
NTP-synchronised, so it left a -3 s UPS offset alone and would not look again for six hours
(`clock offset -3 s; not correcting it, because the system clock is not NTP-synchronised`).
Correct behaviour -- copying an unsynchronised clock into the UPS is how a wrong wake time gets
set -- but the retry is too far off; fixed after this test.

## Not tested

What the UPS does if a wake comes due while the machine is **running**. argond parks any schedule
that would, so this stays deliberately unobserved.
