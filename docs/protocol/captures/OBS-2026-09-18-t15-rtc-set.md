# OBS-2026-09-18-t15-rtc-set

Task T15. **Command 3 sets the UPS real-time clock, from six BCD bytes `YY MM DD HH MM SS`
interpreted as UTC, and the device answers with an empty command-3 frame.** Promotes
`ARGON-UPS-CMD3` from `inferred` to `observed`, and adds `ARGON-UPS-CMD3-REPLY`.

Full output: [`t15-2026-09-18-rtc-set.log`](t15-2026-09-18-rtc-set.log).

## Method

`argonctl rtc --t15 --write`, run by the operator on mains with `argond` stopped, so the tool
was the only reader of the port. Firmware 113, no wake schedule set.

A controlled perturbation rather than a plain set. Setting the clock to the current time
proves nothing if it was already close -- a matching read-back is then indistinguishable from
a write the device ignored -- so the clock was first set to a deliberately wrong, distinctive
time, 1 h 17 min 29 s behind, and read back; only then was the correct time set. The tool had
been rehearsed against the simulated UPS beforehand, including a UPS that ignores the write
while its clock is already correct, which it correctly reported as not confirmed.

## Result

| Step | Sent | Received | Read back | Error |
|---|---|---|---|---|
| baseline (x3) | queries only | -- | 11:18:38 / 40 / 41 | -22, -21, -21 s against the system clock |
| set wrong | `FE 06 03 26 09 18 10 01 33 92` | `FE 00 03 01` | 10:01:35, 10:01:37 | -1 s, 0 s |
| set right | `FE 06 03 26 09 18 11 19 07 7F` | `FE 00 03 01` | 11:19:10, 11:19:11 | +1 s, +1 s |

All times UTC, 2026-09-18.

What this establishes:

1. **Command 3 sets the clock.** A time 4649 s from the truth was read back within a second of
   what was sent. That cannot be a coincidence, a whole-hour time-zone confusion or a stale
   value, which is why that offset was chosen.
2. **The encoding is BCD `YY MM DD HH MM SS` with the year offset from 2000, and the device
   treats it as UTC** -- the same frame of reference command 5 reports in, since the read-back
   matched in UTC with no offset.
3. **The reply is an empty command-3 frame**, `FE 00 03 01` (checksum `FE+00+03 = 0x101`, low
   byte `01`), within the 1.5 s listening window, on both sets. It is not the command-8
   acknowledgement the ledger had inferred for writes. The simulator already replied this way;
   that was a guess, and is now observed.
4. **The clock was 21-22 s slow before the test.** No drift rate can be derived: nothing
   records when it was last set. The vendor's `argonupsrtcd`, which presumably kept it set, was
   retired on 2026-09-17. With the clock now set to within a second at 11:19 UTC, a read a day
   or more later would give one.

## What it does not show

- Anything about **command 6**, the wake schedule. It is still `inferred`, and a separate
  confirmation is needed before scheduled wake can be built.
- Whether the clock survives a **full depletion**. T14 stopped at 9 %.
- The one-second read-back errors in step 4 are at the resolution of the method (whole-second
  device clock, sub-second write phase), not a property of the device.
